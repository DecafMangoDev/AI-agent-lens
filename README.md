# AgentLens

CLI на Go для анализа журналов Codex без модели и сети по умолчанию.

**Я хочу находить ошибки процессов, скрытые за успешным выполнением `exec`, и повторные неуспешные попытки, чтобы решать, где агенту нужна проверка результата или смена способа исправления.**

Исходное задание: [docs/ASSIGNMENT.md](docs/ASSIGNMENT.md). История решений: [DECISIONS.md](DECISIONS.md).

## Запуск

Go 1.26+, только стандартная библиотека.

```bash
go run main.go analyze --input session.jsonl
go run . analyze --input testdata/real/
go run . analyze --input session.jsonl --details
go run . analyze --input session.jsonl --json
go build -o bin/agentlens .
go test -race ./...
go vet ./...
```

Если стандартный Go cache недоступен, используйте `GOCACHE=/tmp/agentlens-go-cache`.

## Что отвечает отчёт

Основной вывод содержит сводку сессии с расходом токенов и временем инструментов, таблицы внешних Codex/MCP-вызовов и до двух наблюдений с адресами событий. В таблицах инструментов показаны сумма времени, медиана p50, p95 и число вызовов с измеренным временем. Время измеряется в секундах между вызовом и результатом; время вложенных операций не приписывается внешним инструментам повторно. Токены всего = вход + выход; кэш уже входит во вход. Неизвестные значения показаны как n/a.

`exec` — **один запуск JavaScript-скрипта**, способный вызвать несколько инструментов. Поэтому число внешних запусков и число внутренних операций не обязаны совпадать. Раньше в таблицу ошибочно попадали рядом реальные вызовы и статические ссылки из кода. Теперь таблицы считают только записи внешних вызовов. Ссылки доступны отдельно через `--details`, с явной пометкой «не вызовы».

`OK` для exec означает, что его оболочка завершилась (`Script completed` в первом служебном блоке). Команда внутри при этом может вернуть ненулевой exit_code. Результаты процессов показаны отдельной величиной: это напечатанные результаты, **не уникальные процессы и не восстановленное число внутренних вызовов**. Один процесс может сначала вернуть управление, а потом завершиться при опросе.

Обозначения: `OK` — подтверждённый успех внешнего инструмента, `ERR` — его ошибка, `?` — статус неизвестен, `WAIT` — результата нет. Наличие ответа само по себе не означает успех. Для MCP используются явные isError; для процессов — exit_code/timed_out. Отсутствующие числа остаются null, не нулём.

## Наблюдения без ИИ

1. **Ошибка внутри успешного exec.** В первом служебном блоке зафиксировано завершение скрипта; в отдельном JSON-блоке результата процесса есть ненулевой exit_code. Отчёт показывает строки, ID и номера блоков. Вывод: надо проверять результат команды, а не только успешность оболочки.
2. **Повтор неуспешной попытки.** Совпали имя инструмента, хеш полного входа и код/хеш вывода неуспешного процесса в разных вызовах. Показываются промежуточные действия. Это точный повтор наблюдаемых данных, а не доказательство неизменности окружения или бесполезности повторной попытки.

При нехватке данных выводится наблюдение об ограничении, а при отсутствии эпизодов — честное сообщение об отсутствии находок. Программа не выдумывает два замечания ради количества. Наблюдения содержат факт и отдельное предложение, что проверить; причины ошибок автоматически не устанавливаются.

## Поддерживаемые данные

Native Codex rollout JSONL из `~/.codex/sessions/YYYY/MM/DD/`. Не путать с stdout `codex exec --json`: это другой формат. Один файл — одна сессия. Для архива: `zstd -dc source.jsonl.zst > session.jsonl`.

Обязателен `session_meta` с id/session_id. Вызовы `function_call` и `custom_tool_call` связываются с соответствующими `*_output` по call_id. Временные метки RFC3339; маркеры task_started/task_complete задают завершённость последнего хода. Каждая запись имеет type и объект payload. Максимум строки — 16 MiB. Каталог: непосредственные `*.jsonl`, без рекурсии и следования ссылкам. Ошибки файлов не пропускаются, исправные файлы продолжают анализироваться.

Подготовка безопасного экспорта:

```bash
go run . prepare --input /path/to/rollout.jsonl --output session.jsonl
```

Сохраняются только идентификаторы, времена, числовые usage, исходы, SHA-256 входов/выводов, размеры, ссылки на имена инструментов и exit_code результатов процессов. Команды, полные ответы, сообщения, инструкции и рассуждения не копируются. `source_line` — строка оригинала; адреса отчёта — строки анализируемого файла. Существующий выходной файл не заменяется.

Для извлечения напечатанных результатов требуется объект с chunk_id, output и exit_code либо session_id. Поддерживаются самостоятельный объект, JSON в строке/текстовом блоке и fulfilled/value от Promise.allSettled. Парсер не обходит произвольный текст рекурсивно и не исполняет JavaScript. Вывод об ошибке относится к зарегистрированному результату; подлинность произвольно напечатанного JSON журнал самостоятельно не доказывает.

## Опциональное мнение ИИ

```bash
export OPENAI_API_KEY='your-key'
export OPENAI_BASE_URL='https://your-provider.example/v1'
export OPENAI_MODEL='your-model'
go run main.go analyze --input session.jsonl --ai --ai-output opinion.json
```

Один POST на `<OPENAI_BASE_URL>/chat/completions`, без повторов, редиректов, инструментов и последующих ходов. По умолчанию base URL — `https://api.openai.com/v1`. Необязательный `OPENAI_REASONING_EFFORT` передаётся явно, только если задан. Конфигурация читается из окружения; `.env` соседнего проекта автоматически не загружается. Адаптер перенесён по схеме `new_agents_hw/agent/client.py`; [официальный контракт Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

Модель получает не весь журнал, а максимум пять сессий с двумя наблюдениями на каждую и первыми восемью адресами событий; строки ограничены, итоговый контекст не больше 24 KiB. Исходные команды, сообщения и результаты не отправляются. Сокращение выборки указано в контексте. Модель просим дать мнение и проверяемую гипотезу, а не объявить причину установленной.

Ответ помечается «МНЕНИЕ ИИ». Точный запрос и ответ сохраняются в новом файле с правами 0600; ключ туда не записывается. Без `--ai-output` используется имя `agentlens-ai-<timestamp>.json`. Контекст сохраняется до запроса, ошибка — после неудачи. Существующий файл не перезаписывается, запрос в таком случае не отправляется. Таймаут — 60 секунд, предел ответа — 1 MiB. При ошибке модели основной отчёт остаётся доступен; код выхода — 1.

Проверено на имитируемом HTTP-транспорте: один запрос, ответ/ошибки API, запрет повторов/редиректов, сохранение контекста и отсутствие ключа в артефакте. Реальное обращение к провайдеру в этой среде не выполнялось.

## JSON, примеры и проверка

Схема `agentlens.session.v2`: sessions, groups, errors; `sessions[].observations` — вычисленные наблюдения; `calls[].process_results` — основания по процессам; `ai` — отдельная интерпретация модели, если запрошена. Старые метрики времени/токенов остаются в JSON. `complete` описывает полноту временных событий и чтения, не успешность задачи и не наличие всех внутренних результатов. stdout с `--json` — один объект, технические сообщения — stderr.

Коды: 0 — завершённый анализ (включая отсутствие находок/предупреждения), 1 — ошибка входа/вывода или ИИ, 2 — параметры. Подробные ID/предупреждения — `--details` и JSON.

- [Три реальные сессии](testdata/real), [происхождение и хеши](testdata/manifest.json).
- [Отчёт по исходной выборке](docs/reports/report.txt), [JSON](docs/reports/report.json).
- [Отчёт с наблюдениями по рабочей сессии](docs/reports/session-metrics.txt), [его вход](testdata/snapshots/session-metrics.jsonl).
- [Ручная сверка](docs/MANUAL_CHECK.md).

Синтетические тесты проверяют найденный эпизод, разные входы с одинаковой ошибкой, отсутствие результата, различие оболочки/процесса, экспорт, временные интервалы и ошибки файлов.

**Статус задания:** CLI и наблюдения реализованы; 12 сравнительных запусков не выполнены из-за ошибки инициализации локального Codex. Предыдущий [протокол эксперимента](docs/archive/experiment/PROTOCOL.md) проверял объединение чтений и относится к раннему вопросу о времени. Он не является проверкой нового вопроса об ошибках: перед сравнением потребуется отдельно зафиксировать изменение проверки exit_code и соответствующие задачи. Эффективность изменения пока не доказана.

## Структура проекта и проверки

```text
main.go, main_test.go    CLI и его модульные тесты
integration_test.go     проверка реальных и синтетических сессий
internal/lens/          анализ и тесты метода рядом с кодом
internal/report/        ASCII-отчёт и тесты представления
internal/advice/        клиент ИИ и тесты HTTP-транспорта
testdata/               реальные, синтетические сессии, manifest
docs/reports/           сохранённые отчёты для проверки задания
docs/archive/experiment/ прежний протокол и материалы, без исполнителя
```

`examples` был каталогом готовых отчётов; теперь они лежат в документации. Старый `experiment` не относится к текущей гипотезе: протокол сохранён в архиве, неиспользуемый runner удалён. Данные тестов находятся в стандартном для Go каталоге `testdata`, который Go не воспринимает как набор пакетов. Пакетные тесты остаются рядом с реализацией; интеграционные сценарии отдельно проверяют все 15 файлов и их ожидаемые наблюдения. Пользовательские `.env`, настройки IDE и сохранённые ответы ИИ при очистке не удалялись.

```bash
make tools       # установить фиксированный Staticcheck v0.8.1 (нужна сеть)
make lint        # форматирование + go vet + Staticcheck
make test        # тесты с race detector
make check       # линтер и тесты
make fmt         # исправить форматирование
make reports     # воспроизвести отчёты в docs/reports
```

[Staticcheck](https://staticcheck.dev/docs/getting-started/) установлен как инструмент разработки, не как зависимость CLI. Версия закреплена в Makefile, используется стандартный набор проверок в staticcheck.conf. В этой среде проверены go vet, gofmt и тесты; загрузка Staticcheck блокируется недоступностью proxy.golang.org, поэтому результат самого Staticcheck пока не подтверждён.
